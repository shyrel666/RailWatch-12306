## 本次落地

### 起售前登录检查

在启用自动提交或自动候补的定时任务中，等待进入起售前60秒、且仍距起售超过10秒时，补查一次登录。即使关闭周期性保活，这项自动交易检查仍会执行。检查与查询共用原来的浏览器任务，不启动并发浏览器操作。

检查返回无法确认或已失效时，清除旧的登录就绪状态并暂停提醒；不让缓存的“已登录”掩盖检查失败。同一轮满足周期保活和临售检查条件时只执行一次。检查结束后重新计算剩余时间。最后10秒内才启动的任务保留已有启动前检查，不再插入一次临售检查；调度等待阶段本身不会在最后10秒发起登录检查。

实现：`railwatch_task.py`、`railwatch_bridge.py`；提示：`src/components/TimerSettings.tsx`。

### 失败组合暂避

普通订单仅在持久化订单记录确认“提交前售罄且未创建订单”时进入暂避。候补仅在重新检查发现目标席别的入口按钮已经消失、尚未执行候补页面动作时进入暂避。组合按本次查询区间、日期、车次、席别和操作类型区分，使用单调时间暂避30秒，到期可重新参与选择。

暂避某车次的二等座预订不影响该车次一等座、其他日期或同席别的候补。明确售罄后，启用候补的任务立即重新查询原订单日期；其他安全重试遵守正常查询间隔。服务端限频与冷却规则继续优先执行。

候补最后的提交按钮不可用、信息回读不一致、需要核验、提交结果未知时，仍交给人工核对。只要记录里已有提交标记，即使适配器返回“可重试”，订单记录层也会将其降为结果待核对，阻止新交易。待支付或已生效的订单继续占有提交权限。

### 候补回退保持现票优先

回退查询原订单日期时，先检查未处于暂避期的其他现票组合，再考虑候补。不会因第一张票售罄就忽略其他车次新出现的现票。

原订单日期的一次有效查询若没有任何可用现票或候补入口，解除回退日期固定，恢复正常日期轮询；起售窗口原有的目标日期聚焦仍生效。超时、核验、过期页面等无效结果不能触发这个决定。

实现：`gui_12306_0.py`、`railwatch_alternate_flow.py`。
