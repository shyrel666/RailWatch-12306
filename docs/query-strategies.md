# 查询优先级的推荐默认策略

更新：2026-09-11。

两种优先级现在应用完整、可保存的参数组合。新配置默认选择「成功率优先」；已有配置保留原来的间隔、超时及开关，不会在升级时被推荐值覆盖。点击一个优先级即可应用或恢复该优先级的推荐值。

## 默认参数

| 参数 | 速度优先 | 成功率优先 |
| --- | --- | --- |
| 适用场景 | 关注起售后的及时响应 | 持续监控、网络较慢时保留较长响应等待 |
| 请求模式 | 快速模式 | 保守模式 |
| 基础查询间隔 | 3 秒 | 6 秒 |
| 查询完成超时 | 20 秒 | 40 秒 |
| 初始随机等待 | 3.0～3.6 秒 | 5.0～7.2 秒 |
| 智能轮询调整范围 | 3～30 秒 | 5～60 秒 |
| 保持会话 | 开启 | 开启 |
| 智能轮询 | 开启 | 开启 |

请求模式也可单独选择。均衡模式采用 5 秒基础间隔、30 秒超时、4～45 秒调整范围，初始随机等待 4.0～6.0 秒。切换请求模式同样应用相应间隔、超时，并开启智能轮询和会话保持；优先级名称继续代表所选偏好，偏离其完整预设时显示「已自定义」。

上述间隔在普通监控中是两轮查询间的等待，实际周期还包括查询响应及页面处理时间。定时起售窗口内，正常响应与未起售提示按查询点击返回后的单调时间计算剩余间隔，扣除已花费的响应和页面处理时间；慢响应不积压补发，异常、限流与服务端等待不扣减。超时不是每轮必等时长：观察到有效的本轮响应后即继续处理。若手动设置的基础间隔大于模式上限，上限扩展至该基础间隔，避免超时反而加速。

## 选择依据与参考来源

1. [py12306 的配置示例](https://github.com/pjialin/py12306/blob/master/env.py.example) 分开配置随机查询间隔、用户心跳和重试次数。本次采用这些职责分开的思路；其中历史示例的 1 秒查询值不作为当前平台认可的频率依据。
2. [AWS SDK 重试策略文档](https://docs.aws.amazon.com/sdkref/latest/guide/feature-retry-behavior.html) 使用有上限的退避与随机抖动，并区分一般瞬时错误和限流信号。本项目沿用已有的错误分类和倍增退避，在各模式中设置不同边界；没有照搬其 SDK 毫秒级参数或完整算法。
3. [Playwright 的自动等待文档](https://playwright.dev/docs/actionability) 强調满足有效条件后继续，并以超时约束最长等待。本项目继续使用当前 Selenium 查询结果验证逻辑；速度模式缩短的是空等和失败后的等待预算，不跳过结果与订单校验。

3 秒／6 秒间隔及 20 秒／40 秒超时是结合本项目现有的 3 秒保护下限、浏览器串行查询、错误退避及结果验证流程选取的工程推荐值，并非来自这些项目的性能对比实验。没有实测数据能证明其为所有账号、网络和起售场景的全局最优，也不能据此推断购票成功率提升。

## 实际行为

- 超时、普通异常及风险信号继续沿用现有限速器的逐步放慢策略；连续五次成功后逐步恢复，恢复过程仍受所选模式的下限约束。
- 成功率优先不再关闭智能轮询，因此在长期成功响应后也不会退化到快速模式的 3 秒下限。
- 初始随机延迟按运行时实际的 ±20% 抖动和上下限计算；运行后会变化，界面明确说明其为初始范围。手动关闭智能轮询时显示实际 ±30% 范围及退避关闭说明。
- 手动修改间隔、超时、模式或开关会保留修改，并显示「已自定义」；切换页面、恢复保存配置时直接使用配置中的优先级和模式，不再通过智能轮询开关推测它们。
- 优先级预设不修改车次、席别、座位偏好、日期范围、乘客、定时目标和交易授权开关。自动提交与自动候补不会因选择成功率优先而自动启用。
- 旧配置缺少模式字段时使用「原有配置」，沿用之前 3～30 秒的智能轮询边界（基础间隔更大时扩展上限），直至用户主动选择新预设。
- 会话保持继续使用现有登录检查周期；官方核验、未知弹窗和不确定订单结果的人工接管行为保持原样。

## 定时、会话与时钟诊断（2026-09-29）

桌面任务点击“开始监控”后立即准备查询页面、创建监控器并完成首轮填参，然后等待完整的北京时间起售时刻。首次查询不先等待轮询间隔。定时起售窗口默认至起售后45秒，期间集中查询所选乘车日期，窗口结束后恢复日期范围轮询；明确售罄后的候补回退仍绑定原订单日期。所选日期不可查询时停止，不静默改抢其他日期。`prepare_time` 为兼容配置，仅参与冲刺窗口判断，不能提前首次查询；`prewarm_lead_seconds` 也不控制桌面主流程的页面准备时刻。保留这两个字段用于旧配置读取，不新增提前点击选项。

保持会话开启时，约每60秒调用官方登录检查；起售前10秒到后5秒的周期检查暂停，减少关键时刻的额外请求。启用自动交易时，准备阶段仍会检查一次登录。登录失效或连续三次无法确认时提示人工处理，不自动重登，也不保证登录永不过期。智能轮询在收到未起售提示时仍遵守当前间隔，因此提前两秒查询可能导致下一次查询落到起售之后。

调度使用系统时钟确定目标，并用单调时钟等待；不使用 HTTP `Date` 偏差调整触发时间。HTTP 辅助诊断先排除缓存、格式异常和测量期间的系统时钟跳变；失败时清除旧偏差和不确定度，避免把旧值当成新证据。其不确定度估计包含秒级日期头分辨率和半个请求往返时间，不能视作精密授时保证。

彩排判断要求偏差和不确定度均为有限数值、不确定度非负且不超过1秒。测量范围整体处于±1秒以内才通过；最小可能偏差超过1秒提示风险，超过3秒提示先核对系统对时；跨越通过阈值或测量误差过大时返回“无法判断”。这些阈值是本地诊断参数。请在启动定时任务前完成系统自动对时，任务等待期间发生明显时钟跳变仍会暂停。

## 多日期策略与耗时统计（2026-10-04）

日期范围为多日时，可选择「按日期顺序尽快候补」「先查首选日期」或「限时扫描多日期现票」。旧配置保留按日期顺序轮询；限时扫描默认预算 30 秒，范围 10～120 秒，预算不会截断官方等待或候补重查。定时起售窗口内仍集中查询所选日期，明确售罄后的候补回退仍绑定原日期。策略不会自动开启交易授权。

运行复盘新增最近最多 200 轮查询的分阶段中位数、P95 和同日查询实际间隔。策略语义、浏览器批量操作、实测结果和验证范围见[第一批效率优化说明](efficiency-phase1.md)。

多组合候补可在自动化设置中单独启用，沿用任务的日期范围及起售／售罄回退限制。候补生效后的订单核对独立设置间隔，默认60秒，出现读取异常逐步放慢至最多600秒。完整行为、清单核验和验证记录见[第二批实现说明](efficiency-phase2.md)。这些设置不会自动开启交易授权。

## 实现与验证

唯一参数表是 `railwatch_policies/query_strategies.json`，由 React 和 Python 共同读取，包含在 wheel 和 PyInstaller 运行时中。配置新增 `query_priority` 与 `request_mode`，经规范化、主查询任务、`QueryConfig`、磁盘保存和运行时恢复完整传递。

- Python pytest：193 项测试、47 个子测试通过。
- CI 使用的 unittest discover：184 项测试通过。
- 前端：107 项测试通过；Electron：34 项测试通过。
- TypeScript 检查、Electron 编译、前端生产构建及 Python 语法编译通过。
- 本地 Chrome 测试验证两种预设、开关、保存、刷新恢复和 1180 像素窗口无横向溢出，无浏览器错误日志；截图位于 `build/strategy-review/strategy-speed.png` 和 `strategy-reliability.png`。
- wheel 构建、隔离安装并加载策略数据通过。
- PyInstaller 构建通过；生成的可执行程序在隔离数据目录中验证默认保守策略、保存快速策略、跨进程重启恢复。构建产物位于 `build/strategy-review/runtime/railwatch_runtime.exe`。
