# v0.4.2 P3 订单历史分页性能修复

日期：2026-09-24。范围：原审查的订单历史分页性能项。基于已完成 P1、P2 修复的工作区，保留既有实施改动；本轮没有修改前端协议或重新打包安装器。

## 修复前的实际证据

当前 P2 版本的每页 20 条历史执行 61 次 SELECT：一次分页查询，加上每条记录的官方证据、最近状态事件和页面核对检查点三次查询。原始审查中的 41 次是增加 P2 检查点之前的计数。

新增 `tests/test_p3_paging.py` 后先在原实现运行，结果为 4 failed、2 passed，确认如下问题：

- `EXPLAIN QUERY PLAN` 返回 `SCAN orders` 和 `USE TEMP B-TREE FOR ORDER BY`。
- 查询次数随每页条数线性增长。
- 一条官方证据之后存在一万条非官方结果事件时，查找最后官方证据约执行六万条 SQLite 虚拟机指令。
- 重新打开旧数据库并不能修复缺失的分页索引。

## 实现

`railwatch_orders.py` 增加三个幂等创建的索引，不改变原有表结构或订单内容：

- `orders_history_sort(updated_at DESC, intent_id DESC)`：按历史顺序读取。
- `orders_history_status_sort(json_extract(result,'$.status'), updated_at DESC, intent_id DESC)`：状态过滤后按历史顺序读取。
- `order_events_official_latest(intent_id, sequence DESC)`：仅包含标记为官方证据的 `order_result` 事件。

深页条件改为 `(updated_at,intent_id) < (?,?)`，SQLite 可以直接定位索引范围，避免从较新的记录开始逐条过滤。游标编码和排序规则不变。

分页先读取最多 `limit + 1` 条订单，再用一次查询读取当前页订单的三类摘要资料；空页仅执行一次 SELECT，非空页执行两次。摘要查询内部按索引查找最新事件，不加载全量时间线，也不聚合其他订单的事件。官方证据查询明确使用专用部分索引：实测仅新增索引时，未经 ANALYZE 的数据库仍可能选择旧的 intent/stage 索引并扫描大量非官方结果。

列表与详情共用摘要组装逻辑，保留按事件序号选择最后官方证据、旧记录回退、P2 内存检查点优先级和隐私字段过滤语义。

## 合成数据对比

命令：

```powershell
python -X utf8 tests/history_paging_benchmark.py --baseline tmp/v042-review-20260924/orders_before_p3.py
```

基准脚本对修复前后的真实 `OrderJournal.history_page()` 执行计数与查询计划采集，再进行七次计时取中位数。数据在临时目录批量生成，包含相同更新时间、10% 状态筛选命中率；每条订单有一条官方事件。前后逐项比较完整返回值，包括所有摘要字段与游标，全部一致。没有访问用户订单库。

本机 Windows、Python 自带 SQLite 3.37.2，十万订单及十万事件，每页 20 条：

| 场景 | SELECT 次数（前 → 后） | SQLite 指令数约值（前 → 后） | 耗时中位数 ms（前 → 后） |
| --- | --- | --- | --- |
| 首屏 | 61 → 2 | 1,400,900 → 1,600 | 69.788 → 0.741 |
| 深页 | 61 → 2 | 708,000 → 1,700 | 26.208 → 0.953 |
| 状态筛选首屏 | 61 → 2 | 530,900 → 1,600 | 64.167 → 1.095 |
| 状态筛选深页 | 61 → 2 | 461,700 → 1,700 | 64.176 → 0.994 |

一万条数据下，修复后上述查询也约为 1,600／1,700 条指令。执行计划确认首屏顺序读取排序索引，深页执行复合游标范围搜索，状态筛选使用对应表达式索引；均无临时排序。SQL 内部仍按当前页条数进行索引查找，不能把两次 SELECT 理解为与页大小完全无关的工作量。

时间仅为本机合成数据、重复读取下的结果，不作为其他机器或生产数据的延迟承诺。回归测试约束查询次数、计划与执行步数，不使用易受机器负载影响的耗时门槛。

原始数据位于 `tmp/v042-review-20260924/p3-benchmark.json`；本轮修复前源码快照位于同目录的 `orders_before_p3.py`。基准脚本不传 `--baseline` 时可独立验证当前实现。

## 验证和代价

- 新增七项测试：页大小 1／20／50 的查询次数、首屏与深页执行计划、大量后续非官方事件、同时间戳分页无重复遗漏、列表和详情证据一致、旧库索引迁移、订单状态更新和结束核对后的索引有效性。
- `python -X utf8 -m pytest -q`：**321 passed，151 subtests passed**，涵盖既有订单交易、恢复以及 P1/P2 后端回归。
- `git diff --check`：通过。

新增索引会增加磁盘与写入维护成本。该十万条合成数据从旧库初始化新索引后，数据库增加 8,851,456 字节（约 8.44 MiB），本次初始化耗时约 303 ms；真实迁移时间取决于原库规模与磁盘性能。索引使用 `IF NOT EXISTS` 创建，后续启动不会重复重建。
