## 实际页面结构

| 字段 | 实际结构 | 实施决定 |
| --- | --- | --- |
| 容器 | `#content_list` | 限定读取范围 |
| 列头 | `.order-panel-head th`，7 列 | 序号、姓名、证件类型、证件号码、手机／电话、核验状态、操作；列头不匹配时 unknown |
| 数据行 | `.order-item-table tr` | 只读可见行；存在隐藏行时不能证明完整性 |
| 姓名 | 第 2 列 `.name-yichu[title]` | title 与可见文字完整匹配，才接受该姓名 |
| 证件摘要 | 第 4 列可见文字 | 浏览器内再次脱敏，仅输出前 2 字符 + `***` + 后 2 字符；不读取 checkbox value |
| 身份核验 | `.verification-status-user[title]` | 必须读 title，单元格 innerText 实测为空 |
| 手机核验 | `.verification-status-phone[title]` | 与身份核验分开，不能拿手机通过图标证明身份通过 |
| 旅客类型 | 可见列已被官方模板注释 | 不存在可直接读取的旅客类型列 |
| 普通联系人的类型 | `.one-edit[data-val]` 第 4 个 `#` 分段 | 只取类型，不点击编辑；1 成人、2 儿童、3 学生、4 残疾军人，来自官方编辑页选项 |
| 账户本人类型 | `.UserSelf` 行没有 `.one-edit` | 保留 unknown，不从“已通过”或年龄推断成人 |

真实账户抽样：页面共 1 页、2 行，其中本人 1 行、普通联系人 1 行；两行身份图标均为“已通过”；普通联系人类型代码为 1，本人缺少类型证据。读取器实际返回 `recognized=true`、分页完整、本人类型 unknown、另一行 adult。上述数字仅用于说明覆盖范围。

普通联系人的资料类型来自渲染行上的元数据，不等同于交易页最终票种。真实下单页的原有回读检查仍须执行。类型代码 4 单独标记 `unsupported_ticket_type`，不得当作成人。

## 核验状态与方案修正

公开模板存在如下分支，不能用“绿色图标”或“不是已通过”作二元判断：

| 模板证据 | 归一化结果 |
| --- | --- |
| `title=已通过` 且 `user-check-success` | passed |
| `title=预通过` | prepassed，保留独立状态 |
| 错误图标 title 表示未经核验 | pending |
| 错误图标 title 表示未通过、资料重复或旧版身份证不受支持 | failed |
| 新文案、缺少 title、未知结构 | unknown |

本账户仅真实观察到“已通过”；其他状态由当前官方模板确认，并在本地 fixture 验证解析，不能写成真实账户验收。

原方案“核验状态不是已通过 → 官方不允许购票”不成立。[官方注册须知](https://kyfw.12306.cn/otn/gonggao/usersNeedToKnow.html?linktypeid=reg) 包含“预通过”可购票的情况，[官方购票说明](https://kyfw.12306.cn/otn/gonggao/onlineBooking.html) 还区分外国护照待核验等情形。彩排应区分明确失败与无法确认：明确未通过可报失败；预通过及证件相关例外保留风险／人工核对，不统一宣称官方禁止购票。

本人票种 unknown 时，普通自动提交按方案给风险提示，留给下单页逐人回读；自动候补缺少成人票种证据时阻止宣称已就绪。不得以导入记录或默认值替代实时证据。

## 分页

官方脚本使用页面自身的联系人查询接口，参数 `pageIndex` 从 1 开始、`pageSize=10`，响应字段 `pageTotal` 控制 `.pagination`；下一页为 `.pagination a.next`。每次翻页重建 `#content_list`，不能缓存旧行元素。1 页时分页容器隐藏，但其中页数和当前页节点仍然存在。

当前真实账户只有 1 页，因此**没有完成真实多页翻页验证**。分页选择器与页大小来自官方脚本；跨页同名场景仅在本地 fixture 验证。无需为制造多页修改真实联系人。

后续读取上限为 10 页／100 人。页数缺失、不连贯、过滤框有查询条件、到达上限仍有下一页时，不能根据局部名单断言姓名唯一或姓名不存在。不同页的同名项必须保留，禁止按姓名去重。

## 演练标签页隔离验证

原方案只设置 `Network.setBlockedURLs` 不足：本机 Chrome 153 的新标签页从 file 导航到本地 HTTP 服务时，服务端实际收到了请求；某个 `Network.loadingFailed` 事件可能仅来自子资源，不能作为整个页面断网的证明。

追加 `Network.emulateNetworkConditions` 的 `offline=true` 后，同一探针满足：

- 演练页仍能打开 file fixture；
- 演练标签页导航本地 HTTP 地址失败，服务端没有收到该请求；
- 异常退出后关闭演练页并切回原句柄，原地址不变；
- 原标签页仍能刷新同一 HTTP 服务，证明断网配置未影响原标签页。

该验证在独立临时 Chrome profile 中完成，不修改真实账户浏览器的网络设置。最初的 URL 阻断试验还尝试了官方登录页导航，不能将该试验记为已证明“零网络”；修正后的断网回归只使用本地服务。

M2 必须使用“URL 阻断 + 标签页离线 + 限制 driver.get 只允许指定 file 页面”的多层隔离；若任一隔离设置失败，拒绝演练。当前验证仅证明上述本地 HTTP 导航及标签页恢复，不代表交易流程、WebSocket、取消及时性全部验收。
