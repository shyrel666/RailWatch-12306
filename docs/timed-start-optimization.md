# 定时起售优化记录

日期：2026-09-29。适用于当前工作区源码；不表示已安装程序或已发布安装包包含这些改动。

## 目标与实现

目标是降低定时起售关键路径中的本地等待，并确保起售窗口查询所选乘车日期。当前继续采用官方页面与单个受控 Chrome，不增加并发查询。

1. **首轮准备前置**：在等待起售前创建监控器、检查查询按钮、选择首轮日期、填写并记录查询表单。到点后复用准备结果，但查询前仍读取当前表单、核验提示和页面身份；用户修改页面时重新填参，不能使用旧状态跳过检查。
2. **集中查询目标日期**：从准备阶段至起售窗口结束（默认起售后45秒），日期范围中的其他日期不参与轮换。提前准备时按目标执行日判断预售窗口，支持前一天准备次日才开放的乘车日期；到点后及每轮查询前仍按当前日期复核。窗口结束后恢复原日期范围轮询；所选日期已不可查询时停止。明确售罄后的候补回退仍使用原订单日期。
3. **移除唤醒后的同步诊断写盘**：`scheduler_wake` 在发生时记录墙钟和单调时间，先放入内存，与查询遥测一起稍后保存。最小批量配置也不会让唤醒事件自身触发写盘。进程硬退出可能丢失未保存的诊断；订单意图、提交标记及确认尝试仍同步保存，恢复与防重复提交规则不变。
4. **减少浏览器往返**：查询前的表单读取、弹窗检查、响应观察器安装从三次命令合并为一次。每轮仍等待本轮有效响应、DOM变化、按钮状态及300毫秒稳定窗口，旧结果和其他请求不能被误认为本轮完成。
5. **减少起售窗口的重复空等**：正常查询和未起售提示在查询按钮点击返回后记下单调时间，将随后响应和页面处理耗时计入该轮间隔。点击前等待按钮可用的时间不抵扣间隔。超时、未知状态、限频及服务端冷却仍执行完整等待；超过周期的慢请求不排队补发。
6. **提高表单与确认就绪检测频率**：定时任务的订单页面就绪轮询等待从100毫秒改为50毫秒，仍检查停止信号和官方确认按钮是否真正可用。此处只读本地页面，不增加官方订单状态接口请求。提交后的订单结果观察仍为原有周期。

## 本机调度对比

同一台 Windows 电脑、Python 3.10.8，各100个15毫秒短期限样本：

| 指标 | 修改前 | 修改后 |
| --- | --- | --- |
| 目标时刻至调度函数返回 P95 | 32.302ms | 11.173ms |
| 目标时刻至调度函数返回 P99 | 33.326ms | 22.376ms |
| 调度器内部记录的唤醒误差 P95 | 17.000ms | 17.000ms |

修改前返回点包含同步 SQLite 提交，修改后返回点只包含内存记录，写盘在测量返回时间后执行。这里比较的是调用方何时能继续运行，不是官方接收查询或下单的时刻。两种时钟的采样与分辨率不同，表中不同指标不能相减推导单步耗时；短期限样本也不能代表长时间等待、网络、浏览器或实际抢票成功率。
