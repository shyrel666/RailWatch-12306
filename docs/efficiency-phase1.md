# 抢票与候补流程效率：第一批实施

更新：2026-10-04。本批完成浏览器批量操作、查询分阶段统计和多日期策略。沿用单浏览器串行执行、查询有效性验证、交易意图持久化与订单结果核对。

## 使用变化

「行程设置」选择多日范围后，可选择以下策略；「购票监控」会显示本次任务实际采用的策略。

| 策略 | 日期顺序 | 何时考虑候补 |
| --- | --- | --- |
| 按日期顺序尽快候补（默认） | 从最早日期依次轮询 | 每个日期检查全部目标现票后即可考虑本日候补，后续日期可能尚未查询 |
| 先查首选日期 | 所选日期优先，之后按距离由近到远；同距离先查较早日期 | 每个日期检查全部目标现票后即可考虑本日候补 |
| 限时扫描多日期现票 | 所选日期优先，之后按距离由近到远 | 各日期都取得有效查询结果且未命中现票，或达到扫描预算后，再处理已发现的候补 |

旧配置默认保留原有日期顺序。选择策略不会开启自动提交或自动候补。扫描预算默认 30 秒，可设置 10～120 秒；从本轮日期扫描开始按单调时钟计算，包含轮询间隔，但不会截断正在执行的查询、服务端要求的等待或提交前重查。如果还没发现任何候补，则继续正常查询。

限时扫描仅记住存在候补的日期，不缓存可提交的页面按钮。需要回到之前日期时，先重新查询该日期，仍先检查现票，然后核对候补入口；入口消失就继续查询。若选中的是刚完成有效查询的当前日期，则复用当前结果并进行原有提交前检查。失败、超时或已失效的结果不会计为“该日期已无票”。候补仍只提交一个已核对的车次、日期与席别组合。

定时起售窗口内仍集中查询所选日期，默认至起售后 45 秒；窗口结束后才应用多日期策略。普通订单明确售罄且允许候补回退时，仍核对原订单日期。已提交或结果不确定的订单不进入新一轮日期竞争。

「订单中心 → 运行复盘」新增查询分阶段统计：查询前准备、查询及结果就绪、读取余票快照、筛选车次与席别、更新显示与最终检查、保存意图与下单准备。显示样本数、中位数和 P95，并单独显示同一日期两次查询点击确认之间的间隔。

统计使用最近最多 200 轮已记录查询。阶段耗时仅汇总有效结果；同日间隔包含失败查询。正常轮询等待不计入阶段耗时，订单页面操作继续由已有下单分步记录展示。历史缺失数据不补算，中断步骤可能仅记录部分，少量样本不代表稳定的尾延迟。

## 实现边界

- 一次读取车次余票与各席别候补入口的可用状态，筛选时跳过无入口的席别，只重新读取可能命中的候补。提交路径仍再次验证当前页面和候选入口。
- 订单按钮的显示、禁用状态和官方确认按钮就绪状态合并读取；普通订单席别先检查所有乘客对应选项，再批量设置并触发变更事件。完整表单读回核对及原生提交点击保留。
- 订单页等待每次轮询只读取一次快照，用同一份证据判断结果和页面是否就绪。
- 分阶段记录在内存中计时，完成后进入已有遥测缓冲；它本身不会触发立即刷盘。查询遥测保留上限仍为 20,000 条，复盘读取限于最近 200 条阶段记录。交易意图、提交标记和结果继续同步保存。
- 日期调度独立为 `DatePlan`；日期策略参数由 Python 与 React 共享的 JSON 提供，贯穿配置校验、保存恢复、任务快照及运行时。wheel 与 PyInstaller 的资源清单均已加入新策略文件。

## 本地对比结果

同机 Chrome 153.0.8010.53，优化前使用实施前保存的工作区源码，包含当时已有的修改。每个场景先预热一次，再测量 20 次；前后顺序执行，没有与其他测试同时运行。候补筛选场景包含整表快照和决策，两个目标席别、仅最后一趟车有可用候补。

| 场景 | 浏览器命令数：前 → 后 | 中位耗时：前 → 后 | P95：前 → 后 |
| --- | ---: | ---: | ---: |
| 1 趟车候补筛选 | 7 → 7 | 43.19 → 42.90 ms | 47.94 → 79.78 ms |
| 5 趟车候补筛选 | 23 → 7 | 141.82 → 46.84 ms | 231.39 → 51.53 ms |
| 20 趟车候补筛选 | 83 → 7 | 517.70 → 50.34 ms | 557.97 → 81.02 ms |
| 100 趟车候补筛选 | 403 → 7 | 2515.41 → 60.78 ms | 2786.03 → 76.76 ms |
| 普通订单本地页面流程 | 36 → 13 | 176.55 → 93.77 ms | 362.67 → 100.21 ms |
| 候补订单本地页面流程 | 13 → 9 | 168.24 → 139.38 ms | 234.06 → 166.10 ms |
| 50 ms 模拟响应的查询就绪 | 7～8 → 8 | 508.03 → 509.91 ms | 523.80 → 529.42 ms |

20 趟车候补筛选的中位耗时降低约 90%，普通订单本地流程降低约 47%。单车场景命令数相同，中位数基本持平，P95 有波动。查询就绪等待基本不变：本批没有缩短结果稳定性等待或提高请求频率。

这些数据来自离线页面，排除了真实服务响应、订单持久化和桌面通信开销；订单场景仅模拟返回待支付结果。不能据此推断真实抢票成功率、候补兑现率或完整购票耗时。

